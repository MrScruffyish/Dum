# Art and sound in Dum

All pictures and sound effects are generated by code when the game starts
(`src/client/textures.cpp` and `src/client/sound.cpp`). You can replace any of them with
your own PNG or WAV file without touching or recompiling the code.

## Quick start

Every picture the game generates can be written out as a PNG, as a starting point to paint
over or to see the size and position things should have:

```sh
./build/dum --export-art "monster_*" --out art --scale 4
```

This writes every monster at 256x256 (4 times 64) into a folder `art/`. Then:

1. Open one, for example `art/monster_goblin.png`, in GIMP, Aseprite, Krita or any other
   paint program.
2. Paint over it, or draw something new on the same canvas (keep the feet on the bottom),
   and save it as PNG with the same name.
3. Copy the finished file into `data/gfx/`. Start the game: your picture is used instead
   of the generated one. (`./build/dum --single --spawn goblin` shows it at once.)
4. Delete it from `data/gfx/` to get the generated picture back.

### `--export-art` options

| Option | What it does |
|--------|--------------|
| `--export-art` | everything, at the generated size, straight into `data/gfx/` (where it **replaces** the built-in art at once) |
| `--export-art "pattern"` | only names matching the pattern; `*` means any text: `"monster_*"`, `"item_*"`, `"monster_goblin*"`, `"wall_*"`, `"*sword*"`. Put it in quotes. |
| `--out DIR` | write to another folder. **Recommended**: a work folder whose files don't affect the game until you copy them to `data/gfx/`. |
| `--scale N` | enlarge N times with sharp pixels (2, 4, 8...), a bigger canvas to paint on. Pictures over 256 pixels are shrunk again when the game loads them, so draw as big as you like. |
| `--anim` | also the walk and death animation frames (`_walk1`... `_die1`...). Left out by default (see below). |
| `--force` | overwrite files that are already there. Without it, existing files are **never** touched, so you can't lose your work by exporting again. |

Exporting always writes the game's own generated art, never your replacements. Names and
ids: `./build/dum_tool ids` lists every monster, item, spell and class with its picture file
name.

Why export into a separate folder: only the files in `data/gfx/` change the game, and a file
there wins over the built-in picture even when you haven't changed it. A later improvement
to the built-in art then won't show up, because your unchanged copy wins. So keep only
finished pictures in `data/gfx/`.

## Picture names and sizes

The sizes below are those of the generated art. You can use other sizes as long as you
follow the rules in the last column.

| Name | Generated size | What it is | Rules |
|------|---------------|------------|-------|
| `wall_brick`, `wall_cave`, `wall_moss`, `wall_dark`, `wall_wood`, `wall_blood` | 64x64 | wall textures (the dungeon picks a theme per room/depth) | power of two (32, 64, 128, 256...), tiles seamlessly |
| `floor_stone`, `floor_dirt`, `floor_tiles`, `floor_wood` | 64x64 | floor textures | power of two, seamless |
| `ceiling`, `ceiling_cave` | 64x64 | ceilings (cave ceiling above dirt floors) | power of two, seamless |
| `door`, `door_locked` | 64x64 | closed doors (fills a whole wall tile) | power of two |
| `door_red`, `door_blue`, `door_green`, `door_yellow` | 64x64 | doors with a coloured lock (vaults) | power of two |
| `rubble` | 64x64 | rubble blocking a corridor | power of two |
| `stairs_down`, `stairs_up`, `stairs_up_ceiling` | 64x64 | floor of stair tiles, light shaft above up-stairs | power of two |
| `monster_<id>` | 64x64 | monster, standing pose | any size, transparent background |
| `monster_<id>_attack` | 64x64 | monster, attack pose (shown while it attacks/casts) | same size as the standing pose |
| `monster_<id>_walk1`, `_walk2`, ... | 64x64 | walk animation, played while it moves (always, for flying/floating monsters) | 1 to 16 frames, numbered from 1 without gaps, same size as the standing pose |
| `monster_<id>_die1`, `_die2`, ... | 64x64 | death animation, played where it fell | 1 to 16 frames, as above; the last frame lies there a moment, then fades |
| `player_<class>_walk1`, ... | 64x64 | walk animation of other players in co-op | as above |
| `player_<class>` / `player_<class>_attack` | 64x64 | how other players see your class in co-op | any size, transparent |
| `item_chest`, `item_chest_open` | 32x32 | chests, closed and opened (drawn 0.45 wall heights tall) | any size, transparent, bottom row on the floor |
| `item_key_red`, `item_key_blue`, `item_key_green`, `item_key_yellow` | 32x32 | the keys | any size, transparent |
| `item_<id>` | 32x32 | items lying on the floor (and the shop sign) | any size, transparent; the whole picture is drawn 0.28 wall heights tall, so leave empty space around small things |
| `hand_fist`, `hand_dagger`, `hand_sword`, `hand_mace`, `hand_axe`, `hand_staff`, `hand_bow` | 128x128 | the first-person weapon in your hand | any size; drawn at the bottom right of the view |
| `spell_<id>` | 32x32 | glowing projectile / explosion of a spell | black = invisible (it is *added* to the screen like light) |
| `arrow`, `bolt`, `pebble` | 32x32 | arrows, crossbow bolts and sling pebbles in flight | transparent |

`<id>` is the id from the data files (`./build/dum_tool ids` lists them all with their
picture names): `[monster goblin]` → `monster_goblin.png`,
`[item potion_heal]` → `item_potion_heal.png`, `[class wizard]` → `player_wizard.png`.
New monsters and items you add to the data files get generated art automatically, and you
can override it the same way. How to add them: [MODDING.md](MODDING.md).

## Drawing your own monster, step by step

You don't need `--export-art` for this. Just put files in `data/gfx/` (create the folder).

1. Find the monster's id: `./build/dum_tool ids monsters` lists every monster with its id,
   its name in the game and the exact PNG file name to use. Or look in
   `data/monsters.txt`: `[monster goblin]` → the id is `goblin`. (`dum_tool ids items` does
   the same for items, and so on.)
2. Draw it at any size (big is fine, for example 512x512; it is scaled down, see *Sizes*) on a
   **transparent background**, standing with its **feet on the bottom row** of the picture,
   facing you. Save it as `data/gfx/monster_goblin.png`.
3. Optional: an attack pose of the same size, `monster_goblin_attack.png`.
4. Optional: walk frames `monster_goblin_walk1.png`, `monster_goblin_walk2.png`, ... (as
   many as you like, up to 16). They are shown in order, over and over, while it moves.
   Four frames is the classic choice: left foot forward, passing, right foot forward,
   passing.
5. Optional: death frames `monster_goblin_die1.png`, `monster_goblin_die2.png`, ... shown
   once at 10 frames per second when it is killed. The last one stays on the floor for about
   a second and then fades. Draw the body ending up on the floor (the bottom of the picture).
6. Start the game. `--spawn goblin` puts one in front of you for a quick look:
   `./build/dum --single --spawn goblin`.

If you only give the standing picture, the game makes walk and death frames from it by
itself (legs swing, wings flap, snakes slither, the body collapses when it dies). Give your
own frames to replace them. If any walk frame file exists, the generated walk frames are
not used at all, and the same goes for death frames.

Animations are shown only when **Options → Animation** is on. With it off, monsters use
the standing and attack pictures and simply vanish when killed.

**All pictures of one monster must be the same size, with the feet in the same place.**
Each frame is scaled the same way, so if the feet move between frames the monster seems
to jump up and down.

### Sizes

**Draw big; the game scales down.** Any PNG larger than 256 pixels on a side is shrunk
when it is loaded (keeping its shape), averaging the pixels so it stays clean. So you can
paint a monster at 512x512 or 1024x1024 and drop it in as it is. Make every frame of one
monster the same size.

| What | Draw at | Used at (at most) | Notes |
|------|---------|-------------------|-------|
| Monsters, players | anything, e.g. 512x512 | 256x256 | Square is easiest. The picture's height is the creature's height. |
| Items | anything, e.g. 256x256 | 256x256 | The whole picture becomes 0.28 wall heights tall. |
| Walls, floors, ceilings, doors, stairs | a power of two: 256, 512, 1024 | 256x256 | Must be seamless. A power of two stays a power of two when shrunk. |
| Weapon in hand | e.g. 512x512 | 256x256 | Shown big at the bottom right of the view. |
| Spells, arrow | e.g. 128x128 | 256x256 | Glow pictures: black means invisible. |

Partial transparency is turned into all-or-nothing: a pixel is see-through if less than
half of it was opaque. Soft edges from your paint program are fine.

How much of the detail you see depends on the 3D view. The GPU renderer (Options →
Renderer: GPU) draws at your full window resolution and smooths shrinking pictures, so a
256x256 monster shows its detail up close. With the CPU renderer at the classic 640x360,
64x64 is about all that's visible. Bigger pictures cost a little memory and loading time,
not speed.

### How sprites are drawn (important when you make your own)

- **The bottom of the picture stands on the floor.** The whole picture is scaled to the
  creature's height in the world: `0.85 × size` of a wall height, where `size` comes from
  `monsters.txt`. Small creatures like rats are drawn in the *lower part* of the 64x64 image
  with empty space above. If you fill the whole image with a rat, you get a big rat. Either
  leave space, or adjust `size` in `monsters.txt`.
- **Width follows the image's aspect ratio**, so a 64x32 picture is half as wide as tall.
- **Transparency:** pixels with alpha 0 are see-through. Every other pixel is drawn fully
  opaque. There is no partial transparency (keeps the crisp retro look).
- **Bats and wraiths** (sprite `bat` / `ghost`) float above the floor. Wraiths are drawn
  with a checkerboard see-through effect automatically.
- **Light:** paint everything **as if in bright daylight**. The game darkens pictures by
  distance and torch light, and flashes monsters red when hit. Spell pictures are the
  exception: they glow and are never darkened.
- **Bosses** get a crown added to the generated picture. Your own picture is used as-is.
- **Exported frames:** `--export-art --anim` also writes the generated walk and death frames.
  If you put those in `data/gfx/` and then change only the standing picture, the old frames
  keep showing the old look while it moves. Delete them, and the game makes new frames from
  your picture. That's why they aren't exported unless you ask.
- Keep a dark 1-pixel outline around sprites. It reads much better in dark corridors.

### Style tips

- At the classic 640x360 the game scales up with sharp pixels, so detail finer than the
  64x64 grid is mostly wasted on monsters further than a few steps away. With the GPU
  renderer at full window resolution, 128x128 or 256x256 pays off.
- Use a slightly limited palette per area (brown/grey stone near the top, darker and
  redder deeper down) to keep the levels coherent.
- Wall textures must tile: the left edge continues the right edge, and top continues bottom.

## Sound effects

Put WAV files in `data/sfx/` (create the folder). Any sample rate, 8/16-bit or float,
mono or stereo. They are converted to mono at load time (the game pans them itself).

| File | Plays when |
|------|-----------|
| `swing.wav` | you swing a melee weapon |
| `hit.wav` / `crit.wav` | something is hit / critically hit |
| `miss.wav` | an attack misses |
| `shoot.wav` | a bow or sling is fired |
| `cast.wav` | a spell is cast (you or a monster) |
| `explode.wav` | fireball / holy burst / explosions |
| `hurt.wav` | you take damage |
| `door.wav` | a door opens or closes, a lock is picked |
| `pickup.wav` | you pick something up |
| `die.wav` | a monster or player dies |
| `levelup.wav` | you gain a level |
| `growl.wav` | a monster wakes up nearby (your early warning!) |
| `step.wav` | your footsteps |
| `stairs.wav` | the party takes the stairs |
| `heal.wav` | you are healed |

Sounds from other places in the dungeon get quieter with distance (silent beyond 20 tiles)
and are panned left/right by direction. Keep effects short (under a second) and trimmed at
the start, or they will feel late. Normalize them to about -3 dB. The game mixes up to
24 sounds at once and soft-limits the output.

There is no music yet. It would go in the same folder later.

## Changing the generated art in code

To change the built-in look instead of using PNGs, edit `src/client/textures.cpp`:
`brickWall()`, `caveWall()` and similar functions make the textures, `humanoid()`,
`caster()`, `rat()` and similar functions draw the monster types, `itemSprite()` draws the
items and `viewModel()` draws the weapons in your hand. A monster's `sprite`, `color` and
`color2` in `monsters.txt` pick the drawing function and the body and eye colors, so you
can get a new-looking monster with no code at all.
